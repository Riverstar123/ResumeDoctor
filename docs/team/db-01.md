版本编辑遵循“父行 FOR UPDATE → 比较 base_version → 插入新内容版本 → 更新 latest”。确认只作用于 latest，重复确认不改变首次时间；已确认旧版本仍可用于新诊断。父行 latest 的复合外键为 DEFERRABLE INITIALLY DEFERRED，允许首次父行和 version 1 在同一事务插入。数据库触发器禁止更新内容、原始 JD 和版本创建信息。

诊断在一个事务中验证档案和所有岗位的归属、确认、可评分要求及重复岗位，再插入 task/diagnosis/items/幂等键。冻结引用使用指定版本；任务输入中的 UUID 规范为小写，保留岗位请求顺序。新编辑不修改历史报告。

幂等唯一键为 `(session_id,key)`，通过 PostgreSQL 唯一索引与 `ON CONFLICT` 竞争，资源与键同事务提交；没有进程锁。JSON 对象键排序、整数型 JSON 数值规范化后计算摘要，路径 operation 使用固定名或小写资源 UUID。上传摘要含文件字节、model_id 和 media_type。同键异请求返回 409，同请求重放先于 busy、后续版本和模型停用检查。

没有扩展幂等表的响应列：`profile_create` 固定还原首次 201、不可变 version 1 和初次 confirmed=false；其余 operation 固定还原 202 及原 task_id/diagnosis_id。新 operation 若引入可变成功状态码，必须先修改存储/映射和测试。M1 的路由、DTO 和状态码无变化，M3/M4/M5 不新增数据库访问。

[数据库文档](../03-database.md) 原有“清理队列”缺少具体表定义，本交付最小补充 `file_cleanup(storage_key,created_at,attempt,next_attempt_at)`。队列只存随机键及重试元数据，不存会话、原始文件名、路径或内容。文件落盘前独立提交清理预约，资源事务回滚后也能回收孤儿文件；文件为随机名、私有权限。解析终态由 worker 消费 `release_document` 后调用清理入口；失败保留队列，按 next_attempt_at 重试。清理和终态交接均按“队列 → documents”取锁，避免相反锁序。所有 API/清理/未来 worker 必须共享同一 UPLOAD_DIR。

会话固定七天、不因访问续期；撤销事务先记录 revoked_at，入文件清理队列并删除资源，定时清理移除墓碑。所有后续提交再次检查有效会话。每会话最多两个 queued/running 任务、同档案一个 chat 任务由数据库事务约束；每分钟 HTTP 写速率限制仍是 API-01 的进程内限流，未交付多进程共享速率计数。

## 运行入口

依赖版本来自 [pyproject.toml](../../backend/pyproject.toml)、[uv.lock](../../backend/uv.lock)、[compose.yaml](../../compose.yaml)：Python 3.12.13、uv 0.11.15、PostgreSQL 17.11、SQLAlchemy 2.1.4、Alembic 1.20.0、psycopg 3.3.6。未更新锁文件。

```sh
uv sync --project backend --locked --extra database
# 在私有 backend/.env 填写 DATABASE_URL，使用 PostgreSQL + psycopg。
make migrate
make dev-database
make cleanup-db
```
