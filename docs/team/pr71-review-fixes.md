# PR #71：长输入处理修复

针对 A 在 [评审意见](https://github.com/Riverstar123/ResumeDoctor/pull/71#discussion_r4476812708) 中指出的同步校验卡顿，基于原 PR 提交 `69e9f79` 修复。日期：2026-11-05。

## 问题与改动

工具名称允许空格，后续分隔符也允许空格；遇到无法识别的动作时，原正则会反复重新分配同一段空格。同一引用还会按要求条数重复解析，使 worker 的其他异步任务等待。

- 工具名使用不会回退的匹配；动作从中文字符开始，保持原有 Latin 工具名边界。含空格、加号、井号、句点和连字符的工具名仍可识别。
- 同时收紧动作与对象之间的回退，避免长动作序列遇到非法结尾时出现同类开销；保留至少一个对象字符及原有句式解释。
- 每次校验先按完整引用分组，每段引用只解析一次，成功和失败结果均复用。分组仅存在于本次调用，不跨请求缓存岗位内容。
- 原始 quote、输入 DTO、忽略状态与重要性规则不改写；只有同一完整引用中的明确工具应用才使用既有去重逻辑。前端、接口、依赖、提示词及评分公式未改动。

## 复现与性能对照

输入 `"用 Python" + " " * 10000 + "，分析数据"`，包含 10,013 个字符，小于 JD 的 20,000 字符上限；构造两条 Python 要求后调用 `validate_job_content`。

- 修复前新增性能回归先失败：单次校验 **5.279 秒**，超过回归测试的一秒宽裕阈值。
- 修复后同输入测得 **0.000151 秒**；长空格加非法尾标点为 **0.000121 秒**，6,000 次重复动作加非法结尾为 **0.000545 秒**。
- 独立异步对照：原定 10ms 的计时任务，修复前实测 **10.660218 秒**，修复后 **0.008683 秒**；该轮校验分别为 **10.660114 秒 / 0.000122 秒**。此轮与其他测试同时运行，机器负载影响绝对耗时；不能将本机数字当作线上响应时间保证。
- 对照原提交与修复后的 396 个短句，规范化工具名称、动作、对象及是否匹配均一致；包括多词工具名、不同空白、动作串及非法尾部。

以上为本机 Python 3.12.13、合成数据的独立测量。性能回归使用一秒预算而非毫秒阈值，以留出机器负载余量。
