# SC-02：要求匹配交付

对应 #18，D（mysteriesy）实现，用户指定 A（Riverstar123）评审。此次用户明确要求交付全部 D 任务，基于 SC-01 分支准备实现；#11 合并和 C 的 #10 验收仍是团队最终接入的前置。本 PR 不代写 C 的结构化模块，不声称这些前置已通过。

入口：`ScoringService` 实现公共同步 `ScoringPort`；也可直接调用 `assess_requirements(profile.content, job.content, "matcher-v1")` 和 `calculate_score(..., "coverage-v1")`。M2 必须先核实快照已确认、属于同一会话；M4 不查询数据库、不调用模型。

受控词典随 matcher-v1 发布，只处理 NFKC、首尾/连续空白、大小写和 JS/JavaScript、TS/TypeScript、Postgres/PostgreSQL 等价名。Python 不等于机器学习，SQL 不等于 SQL Server，C++ 不等于 C；其余语义不可判定时 unknown。has_skill 仅在 project/experience 且 applied、有有效原文引用时 met；仅自述 partial；明确否认 unmet；冲突 unknown。has_evidence 不产生 partial。

年限只累计 subject 等价的 experience/project，按 [start,end) 并集；正整数月数达到全值/半值/不足半值分别 met/partial/unmet。只对 completed=false 的明确未结束经历将缺失 end 固定为 as_of_month；未知是否在职、日期缺失/倒置/超出确认时点都 unknown。没有使用今天日期。学历使用明确完成的最高序列，较低学历 unmet；符合阈值但未明确完成且 JD 没接受在读时 unknown。少量明确“接受在读”表述可参与判断，不匹配“不接受在读”，其他复杂条件先由 C 拆分确认。

`prepare_job` 是 C 可调用的确认前辅助函数，返回副本、warnings、merged_ids 和 requires_confirmation。重复键为规范化 operator/target/subject/category，相同重要性只计一次；冲突草稿保留 must 并要求重新确认，直接传冲突旧稿给 matcher 会抛 `REQUIREMENTS_NEED_CONFIRMATION`。C 应把警告给用户看，存为新版本确认后再诊断。原始快照不修改。ignored 要求及明确个人属性不进入分母，忽略原因留在准备后的草稿；混合个人属性/技能要求请先拆分，普通“照片处理”技术不被当作个人照片。

事实/证据 ID 重复或引用悬空拒绝评分，不能凭不存在的证据得分。reason 和 evidence_ids 均可追溯。来源 quote 是原文子串、学历 value 和其他提取语义仍由 C 验证；公司背景不参与匹配。

验证命令：`backend/.venv/Scripts/python.exe -m pytest backend/tests/scoring -q`，或锁定 uv 对应命令；完整测试与实际结果写入 PR。没有验证 C/E 真实模块、数据库、HTTP 诊断或真实模型。正常样例沿用 [仓库 Profile/JD](../examples/README.md)，失败例为仅包含 ignored 要求，返回 `NO_SCORABLE_REQUIREMENTS`。

2026-10-12 实测：Windows / Python 3.12.13 / cp936 / PYTHONUTF8=0，M4 专项 63 passed，完整 pytest 97 passed；契约检查 36 个 Schema / 4 份样例通过；Ruff check / format --check 通过。边界包含同义词不误配、半月数阈值、并行/间断/未知区间、在读否定表述、学历冲突、重复要求、引用非法、个人属性和提示注入。

## A 评审修复：去重前核对在读资格

按 [A 的行内评审](https://github.com/Riverstar123/ResumeDoctor/pull/40#discussion_r4245212535) 修复：原去重键不含 quote，但学历匹配用 quote 的在读条件，不能用 ID 选第一条后丢掉相反条件。保留既有 operator/target/subject/category 键，在选代表项之前用与学历匹配相同的有限条件解析器检查 accept/reject/unspecified；条件不一致或单条原文自相矛盾时保留整组原始要求，不合并，warnings 标明资格冲突且 requires_confirmation=true。重新准备该草稿仍会要求确认，直到 C 引导用户澄清、形成新版本。

直接评分冲突稿返回 REQUIREMENTS_NEED_CONFIRMATION，不由 ID 决定 100 或 0 分。相同条件的不同表述仍正常去重；否定中包含的“接受在读”不当作肯定条款。没有扩展共享 DTO 或 HTTP 字段。C 接入 prepare_job 时应检查 requires_confirmation，并展示原始 requirements 和 warnings；不能只传准备后的 content 而忽略确认状态。

修复验证：新增反例在修复前 5 failed；修复后 M4 专项 71 passed，全后端 105 passed，公共契约及 Ruff 通过。Windows / Python 3.12.13 / PYTHONUTF8=0。测试另外覆盖相同资格不同表述仍可去重，原始输入不被修改。
