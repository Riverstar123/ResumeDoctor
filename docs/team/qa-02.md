## 验收证据与边界

| 要求 | 实际执行 | 结论与限制 |
|---|---|---|
| T02 异常输入 | 新增测试将损坏/无文本/超页 PDF、穿越 DOCX 经上传 API → Worker → 实际解析器；核对安全错误、无草稿、无模型调用、句柄关闭、原件清理 | 场景内通过；文件大小、展开限制、XML 外部实体、超时及取消继续复跑既有 `test_documents.py` 等回归 |
| T15 资料隔离 | 用真实文件生成档案、JD、诊断和导出，再换另一会话进行读取、修改、确认及导出 | 另一会话返回 404，无原文/评分泄漏，原会话内容与导出不变；使用实际 API/数据库，非模拟授权 |
| T16 撤销期间有后台任务 | 在实际解析后，用事件暂停模型；HTTP 删除会话、清库、删文件，再允许模型真正返回结果 | 旧 cookie 失效，迟到结果不恢复档案、消息、任务或原件；不是仅取消模型等待 |
| T16 到期期间有后台任务 | 保留到期 session/task 行及有效任务租约，先放行模型、核对无写回，再触发 HTTP 过期检查与清理 | 通过；能区分“会话有效性拦截”与“数据库外键已删除” |
| 原件终态/兜底、会话到期 | 复跑既有 `test_postgres.py` 的终态释放、删除失败重试、24h 兜底、固定七天会话清理，以及 Worker 原件释放测试 | 通过；时间边界使用可控时钟/数据库时间，不是持续运行七天，也不证明系统长期停机时仍能删除 |
| T17 提示与数据边界 | 恶意文本与正常安全研究文字均经实际文档解析、M3/M4/M5；受控模型另返回伪造引用、改分字段、越权引用等违规结果 | 可核验的字段/引用/评分防线通过；不能证明真实模型会正确理解所有恶意文字或语义 |
| 模型请求隐私 | 检查档案提取、对话、JD、报告四种实际发出上下文；保留旧联系方式证据但仅过滤发送副本 | 常见联系方式测试通过，冻结快照不变；有限模式匹配不代表完整匿名化，真实网关仍须明确隐私策略 |
| 日志与错误 | 检查调用元信息、捕获日志、HTTP 任务错误与数据库错误字段；异常包含合成密钥、路径与原文标记 | 场景内无泄露；不把 API 正常返回本人资料与“日志无原文”混为一谈 |
| HTML 与页面 | 后端导出转义 HTML；实际 Edge 检查报告、JD、证据等文字，无危险 DOM/执行计数/探针图片请求；同一页面切换模拟 404 后清空旧报告 | 后端导出与浏览器呈现分别通过；浏览器模拟接口不证明后端隔离，也不是完整浏览器→真实数据库端到端验收 |

Markdown 导出的保证是转义原始 HTML。它仍保留用户文字中的 Markdown 链接/图片语法，

## QA25-01：M5 邮箱过滤性能缺陷，待 E 修复

**状态：已复现、未修复；负责人 E，修复后 C 复验。建议 P2。**

位置：[reporting/privacy.py](../../backend/app/reporting/privacy.py) 的 `_EMAIL` 与
`filter_report_context`；[reporting/service.py](../../backend/app/reporting/service.py)
先同步过滤，再调用执行输入限额检查的网关。

邮箱正则没有匹配失败后的快速推进：长串允许出现在邮箱本地部分的字母不含 `@` 时，
会从每个后缀重新尝试匹配。实际输出完全相同的无邮箱文本，也会消耗大量 CPU。
当前默认 fake 报告过滤受影响；真实模式是否受影响取决于调用方显式提供的策略，
本轮不据此推断真实供应商配置。

最小复现（在锁定 Python 环境、仓库根执行脚本；子进程超时会被终止，不无限等待）：

```python
import subprocess
import sys

program = """
from app.reporting.privacy import filter_report_context
value = 'a' * 100_000
assert filter_report_context({'evidence': [{'quote': value}]}) == {
    'evidence': [{'quote': value}]
}
"""
subprocess.run([sys.executable, '-B', '-c', program], cwd='backend',
               timeout=6, check=True)
```

本次实际结果：`TimeoutExpired`，六秒 watchdog 终止；没有调用模型或网络。
这不是“供应商慢”，输入限额尚未来得及检查就发生了同步过滤阻塞。

C 的 M3 同类问题已修复：先增加独立子进程预算回归，旧实现 6 passed / 1 failed，
失败为六秒 watchdog；修复后 7 passed，整组耗时 0.73 秒。
建议 E 对照本轮 M3 修复采用“邮箱分支或整段非邮箱文本”推进方式，
并验证相邻邮箱、Unicode、常见联系方式与长文本。**不要只加起始负向边界**，
它会漏过滤 `a@b.co+z@domain.invalid` 之类相邻邮箱。
未跨模块修改 E 的业务，也未为了测试绿色删除或隐瞒此项缺陷。
