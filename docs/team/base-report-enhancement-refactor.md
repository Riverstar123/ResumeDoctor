# 基础报告与按需建议增强

本次重构延续 PR #76。基础诊断与模型增强具有独立生命周期，增强失败不能撤销已经保存的评分、解释或已通过建议。

## 产品行为

- 确认档案与岗位后，基础诊断按冻结版本评分并生成摘要、缺口与证据说明，不调用模型。
- 用户在报告页主动选择模型和目标要求，再请求当前岗位的建议。一次选择批量生成，逐项核对，不对每条建议单独重复发送整份材料。
- 刷新和重复点击读取原任务；同一冻结项、范围和生成配置的请求复用已存任务，不因为换一个幂等键再次付费。失败结果不会自动重试。
- 前端历史记录仅用于提示；是否复用由服务器按模型映射、提示版本和增强策略决定，避免配置更新后被旧按钮状态永久挡住。
- 生成、审核异常只显示在建议区域。已有基础报告可查看和导出；先前通过的建议不因后续失败被清空。
- 档案变更需要新诊断，历史快照不改写。此重构不更改毕业日期规则、评分系数或用户档案确认步骤。

## 实现边界

基础报告复用 `reporting/explanation.py` 的程序解释和 `validation.py` 的确定性校验。程序模板有独立版本；纯规则结果不伪造模型元数据。

可选增强使用独立后台任务与持久记录，关联既有诊断项。公开状态包含排队、运行、成功、部分保留和失败。基础报告仍保持成功；整体模型审核损坏时不发布本批新增建议。

增强采用私有受控计划：选择已有事实、要求与操作。模板建议由程序渲染；自由经历改写继续接受语义审核。证据编号和原文对应并不等于语义正确，不能因此免除自由改写审核。基础摘要和缺口不再交给模型重新裁决。

每批最多六项候选。突出证据及自由改写必须绑定一条已确认的正向事实和当前已满足/部分满足的要求；原文从该事实与本项评分证据的交集中选择。未知要求只生成核对提示，不能据此写成用户缺少能力。自由改写审核保留该事实的全部证据上下文，不能只读抽取句而忽略限定语。

完整的输入、事实与证据限定上下文仍保留，防止片段截断导致否定、限定或全局已有信息丢失。选择范围限制建议目标，不把它当成已证明的完整 token 压缩。模型原始正文不写入普通服务日志。

## 接口与兼容

`POST /diagnoses` 可不传 `model_id`，新创建诊断只生成基础报告。报告的 `report_template_version` 区分程序模板；旧模型生成记录按原版本读取。

`POST /diagnoses/{id}/items/{item_id}/enhancements` 接收 `model_id` 与可选 `requirement_ids`，返回 `task_id`。空范围表示当前岗位全部有效要求。每次请求先检查会话归属、冻结项与要求范围，再复用或创建任务。

读取诊断返回独立 `enhancement` 状态。任务故障信息与已发布结果的模型来源分开，失败模型不能冒充先前建议的来源。导出包含基础结果、已有建议及当前增强状态。

旧报告不直接进入付费增强，返回 `LEGACY_REPORT_REQUIRES_BASE`，页面引导使用原快照先生成基础报告。新批次按持久化序号合并，避免相同时间戳下顺序变化。不同配置同时请求同一岗位时返回 `ENHANCEMENT_BUSY`；正在处理的原任务继续执行。

SQL 持久化增加增强记录，显式升级 SQLite schema，并提供 PostgreSQL Alembic 迁移。新任务与旧排队任务区分执行模式；迁移不重写历史报告和档案。上线应先完成迁移验证、当前提交复审，再从合并后的 main 打包。

## 费用与失败策略

基础报告生成使用零模型请求。受控模板计划正常一次 HTTP，生成失败重试后最多两次；含自由改写正常两次，生成失败重试后最多三次。审核只请求一次，任何审核失败都不补发以寻求批准。复用任务不再次请求模型；本地 replay 和模拟响应验证不产生供应商费用。

可定位的条目问题只略去该条；整个计划无法解析、审核损坏或漏项时，本批增强仍失败，但基础报告和此前已发布建议保留。数据库任务租约失效后不自动重发可能已经付费的请求。当前没有“强制重试相同配置”的入口，同配置失败记录也复用；改变选择范围、模型配置或创建新诊断后才能发起新的增强。

这不是整条用户流程零费用：简历/JD提取、对话和主动增强仍可能调用模型。具体节省比例需要真实使用数据，不能以测试请求数推算供应商账单。

## 验收要求

- 模型目录不可用时，新基础报告仍可完成、查看和导出，报告阶段没有网关调用。
- 同一增强重复点击、并发请求、刷新与已完成复用不创建重复模型执行。
- 新增强失败不影响基础状态、冻结评分和先前通过内容；不完整审核不发布新建议。
- 会话隔离、要求范围、任务租约、超时回收、重启与资料清理继续有效。
- 新旧数据共存；迁移保留原有资料，SQLite 与 PostgreSQL 的验证结果分别记录。
- 前端模型选择只影响增强；基础报告、建议状态、导出及历史文案保持一致。
