# QA-03 假模型端到端验收与缺陷收敛

日期：2026-10-28。对应 [Issue #26](https://github.com/Riverstar123/ResumeDoctor/issues/26)
（`[E][QA-03] 假模型端到端验收与缺陷收敛`），分支 `e/26-qa-03-fake-e2e`，执行人 E（y1324-cyber）。

## 结论与边界

QA-03 浏览器验收现分**两套覆盖范围不同**的套件，均为真实浏览器 UI、不使用浏览器 stub、
不调用外部模型；二者并存，不互相替代：

1. **轻量套件（`playwright.qa03.config.ts`，8 用例）**：真实 FastAPI 的 INT-01 合成装配——
   进程内 `Platform`/`FakeTaskExecutor` + `SyntheticIntake`（固定合成提取，上传件只要求
   `%PDF-` 魔数，并非真实 PDF）+ `GatewayReporting` + 内存仓储，不需要 PostgreSQL 或凭证。
   它证明的是 HTTP/UI 契约、错误码、版本/幂等/Origin 守卫与前端交互，**不证明 INT-02 交付栈**
   （真实文件解析、`ReportService` 校验、正式 Markdown renderer、数据库队列、独立 worker）。
2. **正式栈套件（`playwright.qa03-db.config.ts`，5 用例，本轮新增）**：真实 UI → http 模式
   Vite 同源代理 → `app.database.create_app`（PostgreSQL，`business_modules`：
   `IntegrationFakeGateway` + `GatewayCatalog` + `ReportService` + `ScoringService`，
   每任务 `GatewayIntake` 真 PDF/DOCX 解析）→ **独立 worker 进程**（`tests.e2e.worker_real`，
   轮询数据库队列、租约/心跳/清理全部走交付实现）→ 启动器自管的一次性临时 PostgreSQL。
   只有模型调用替换为只认登记合成素材的 fake 网关；失败/同步开关只来自服务端进程环境。

- fake 范围内（T01–T21、T23）的 INT-01 契约由轻量套件固定；真实解析/渲染/持久化/独立 worker
  侧由正式栈套件固定，结果见下表。
- **T22 真实模型 Web 演示不属于本轮**，按 Issue 明确留给 AI-03 的显式真实验收；本记录不声称其通过。
- **T14（worker 崩溃后租约接管的并发场景）**仍以 `make test-db` 的 `test_jobs.py` /
  `test_postgres_concurrency.py` 为准（本轮全量 792 项含这些条目，均在临时 PostgreSQL 上通过）；
  正式栈 e2e 额外实证了「独立进程 worker + 数据库队列 + 运行中撤销栅栏 + 物理清理零写回」。
- T16 的撤销语义在两套套件中都有实测；正式栈版本按 A 的评审意见用**旧 cookie 独立重放 401 +
  十表零残留**证明，而非仅靠新会话 404。
- 本轮未发现需要新开缺陷单的 P0/P1：所有探测结果与 OpenAPI、评分契约及错误码约定一致。
  唯一“意外”是 SyntheticIntake 的内部码 `UNKNOWN_SYNTHETIC_INPUT` 在任务边界被按契约脱敏为
  `INTERNAL_ERROR`——这正是 M2 既有错误净化规则（`task_error` 只放行公开码集合），非缺陷。

安全约束：故障开关只存在于后端进程环境（与 FakeModelGateway「失败只来自服务端注入」同一规则），
请求体、请求头和 JD/简历文本都无法影响它们；正式栈网关只认登记合成原文，未知输入明确失败。
控制面 `/api/e2e/*` 只挂载在测试启动器中、仅监听 127.0.0.1，生产装配不 import 测试模块。

### 对 A 两条评审意见的处理

1. **轻量套件不覆盖 INT-02 交付栈**（A 的反例：把 `ReportService.generate_report`、
   `export_markdown`、`GatewayIntake.extract_document` 改成抛错、`Platform.revoke` 改成空操作，
   8 个浏览器用例仍全过；「%PDF-14」假文件会让真解析器抛 PdfReadError）：
   - 新增正式栈套件，基于 `app.database` + 独立 worker 进程 + 专用临时 PostgreSQL；
   - 上传件改为 `tests.platform.int02_fixtures` 产出的**真 PDF/DOCX**（真解析、真分页定位
     `page:1/2/3` 与 `DOCX_PAGINATION_UNVERIFIED` 警告），模型仍只替换为 fake；
   - 报告路径走 `ReportService.generate_report`（结构/语义/冻结评分校验）与正式
     `app/reporting/markdown.py` 导出，断言其固定标题与状态文案；
   - 轻量套件保留但在本记录与文档中准确标明只覆盖 INT-01 适配层与 HTTP/UI 契约。
2. **「新会话 404」不能证明撤销生效**：`real-db-revoke.spec.ts` 删除前保存**旧会话 cookie**，
   删除后用 `request.newContext()` 独立请求上下文重放旧 cookie，断言两个业务端点均
   401 `SESSION_EXPIRED`；同时通过服务端屏障让原 diagnosis_report 调用停在飞行中，放行后等
   worker 的 `iteration_done` 轨迹，再在数据库侧逐表复核该会话十张业务表（profiles、
   profile_versions、jobs、job_versions、tasks、diagnoses、diagnosis_items、idempotency_keys、
   messages、documents）零残留——没有任务结果、档案或诊断迟到写回；新会话 404 保留为
   跨会话隔离检查。

### 一次性 PostgreSQL 的准备

正式栈套件不需要 Docker，但需要 EDB 便携版 PostgreSQL（与 QA-02 同源）：

1. 从 [EDB 便携版页面](https://www.enterprisedb.com/download-postgresql-binaries)下载
   Windows binaries zip，解压到本机**英文路径**（中文路径曾导致 initdb 失败）；
2. 设置 `RD_QA03_PG_HOME` 指向解压后的 `pgsql` 目录（需含 `bin/initdb.exe`）；
3. 启动器自动 `initdb -U postgres -A trust -E UTF8 --locale=C`、启动只监听 127.0.0.1 的
   集群（运行期根目录默认 `%TEMP%/rd-qa03`，文件锁单飞，可被中断后的重跑经
   `postmaster.pid` 接管），按变体建库并 `alembic upgrade head`；不注册系统服务。

本次使用 PostgreSQL 17.11，下载归档 SHA256：
`6eabdf00d2893713b75db4336a23c3fdf505f056e217ec6e2e95d901750cfea3`
（340,719,294 字节）。与 QA-02 记录的 `80379b2c…` 不同——是不同时间下载的归档；
该指纹仅用于记录本次文件，并非声称与发行方签名进行了独立核验。

复现方式：

```bash
# 轻量套件：不需要 Docker/PostgreSQL/凭证
cd frontend && npm run test:e2e:qa03     # 等价 make test-e2e-qa03；首次需 npx playwright install chromium

# 正式栈套件：先准备便携 PG（见上），再执行
RD_QA03_PG_HOME='C:\path\to\pgsql' npm run test:e2e:qa03:db   # 等价 make test-e2e-qa03-db
```
