## 协议与失败行为

- `POST {LLM_BASE_URL}/chat/completions`，Bearer 凭证；`prompt_context["prompt"]` 为 system 消息，其余数据与调用方 JSON Schema 为 user 消息；`temperature=0`、`response_format={"type":"json_object"}`；报告 `max_tokens=3000`。
- 只承诺 OpenAI-compatible Chat Completions；其他协议必须新增适配器。
- 单次调用超时（调用方传 45 秒，超时不重试）；429/5xx/网络错误与非法 JSON/不符 Schema 共用一次重试预算；401/403/404 等配置错误不重试，映射 `MODEL_UNAVAILABLE`。
- 输入上限沿用 AI-01：报告 20,000、提取 30,000 字符，超限在请求前失败。
- 密钥只进入 Authorization 头；公开 `ModelList`、异常消息与 `GatewayCall` 记录都不含 key/base URL/原文。

## 2026-10-25：C 复审两项 P2 修复

C（`huih02427-cmyk`）在 PR #56 对 `9705668` 请求修改，两项均已在本地复现并修复：

1. **real 模式遗漏 `LLM_MODEL` 仍使用演示默认值**：`Settings.llm_model` 原默认 `fake-default`，real 模式会被当成实际模型名发给供应商。现在默认值改为空字符串，`.env.example` 同步留空；real 模式另外明确拒绝旧演示占位 `fake-default`，即使私有 `.env` 仍保留该值也会在装配阶段报 `MODEL_UNAVAILABLE`。fake 模式不读取该字段，行为不变。
2. **非数字端口绕过配置校验**：`_valid_base_url` 现在访问 `urlsplit(...).port` 并构造 `httpx.URL`，在配置阶段拒绝 `:abc`、越界端口和控制字符；`_post` 另加 `httpx.InvalidURL` 兜底映射为 `MODEL_UNAVAILABLE`，不再向调用方泄漏原生异常。错误只给出变量名，不回显端点。

新增回归：省略 `LLM_MODEL`、`fake-default` 占位、`:abc`/`:65536`/控制字符 URL 均在装配阶段失败；合法显式端口（`:8443`）仍可正常请求。复跑 `tests/llm` **33 passed**、后端全量 **620 passed, 3 skipped**、契约 `pending=[]`、Ruff check 与 format（106 文件）通过。仍无真实供应商调用，也未执行 PostgreSQL 测试。
