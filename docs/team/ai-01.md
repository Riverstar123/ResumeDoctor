## 关键设计

- **单一入口**：`FakeModelGateway.generate_structured(task_name, prompt_context, output_schema, timeout_seconds, *, context)` 实现 [ModelGateway 端口](../../backend/app/contracts/ports.py)，四类 `task_name` 与能力名一致。
- **失败与预算**（[06-ai-contract.md](../06-ai-contract.md)）：单次调用超时即 `MODEL_TIMEOUT`；供应商 429/5xx（`provider_unavailable`）与非法 JSON（`invalid_json`）共用**一次**重试预算并短退避；输入超限直接 `INPUT_TOO_LONG`，不静默截断。常量 `RETRY_BUDGET=1`、`INPUT_LIMITS`（报告 20,000、提取 30,000）。
- **失败只来自服务端注入**：`failures` 由构造参数给出（`timeout`/`invalid_json`/`provider_unavailable`），用户经历、JD 或模型输出不会触发开关，与 `FakeTaskExecutor` 同一约定。
- **目录无密钥**：条目只含公开 id、显示名、provider、能力、实际模型名；返回的 `Model`/`ModelList` DTO（[contracts/models.py](../../backend/app/contracts/models.py)）天然没有 key/base_url 字段。默认条目 `demo-model-a`，沿用 API-01 的 id，避免 #13 集成时改变 B 的前端。
- **合成素材与冻结样例逐字一致**：来源 ID `manual-revision-1`、原文与三条引用、岗位原文都与 [docs/examples/profile.json](../../docs/examples/profile.json)、[docs/examples/job.json](../../docs/examples/job.json) 和 M3 合成端口相同，C 用既有演示原文即可接入；一致性由 [test_cross_module.py](../../backend/tests/llm/test_cross_module.py) 固定，任一侧漂移即失败。
- **输出结构冻结**：[llm/schemas.py](../../backend/app/llm/schemas.py) 是 task_name → 输出结构的唯一来源，四类任务的 JSON Schema 由 `task_output_schema(task_name)` 提供；`profile_chat` 的包装结构（`assistant_message` + `profile_content`）由 `ChatOutput` 冻结，不再借用 `ProfileContent` 的 Schema。
- **`output_schema` 参与校验**：调用方传入的 Schema 必须与冻结结构一致，否则在任何模型调用前以 `MODEL_OUTPUT_INVALID` 失败，不按 task_name 静默套用另一种结构、也不消耗重试预算；结果按同一份冻结 DTO 落数据（与 M2 `port_dto` 同一模式）。比对只在 Schema 节点忽略 `title`/`description` 文档注释，字段名与约束全部保留；`task_output_schema` 返回深拷贝，调用方调整自己的 Schema 不改变冻结基准。支持任意 JSON Schema 由 AI-02 的真实适配器交付。
- **调用记录**：`GatewayCall` 只保留 task_name、model_id、prompt_version、attempts、outcome、耗时、输入字符数，不记录原文、密钥或供应商回显。

## 评审修复（P2 第二轮，A 于 PR #46 复审行内意见）

复审基于 `31aeaab`。两项问题都出在 [llm/schemas.py](../../backend/app/llm/schemas.py) 的 Schema 比对与取用，均可使「结果不符合调用方 Schema 却记 `outcome=ok`」。

| 评审意见 | 处理 | 证据 |
|---|---|---|
| 递归忽略 `title`/`description` 会误删同名业务字段：`properties.title` 改成 integer、`$defs.Gap.properties.description` 改成 integer 仍被判为同一结构并返回 `ok` | `_data_shape` 改为按 JSON Schema 结构遍历：只在真正的 Schema 节点丢弃非空字符串的 `title`/`description` 注释；`properties`/`patternProperties`/`dependentSchemas`/`$defs`/`definitions` 按「名称 → Schema」映射处理，键（字段名）与约束全部保留；`items`/`not`/`allOf` 等嵌套子 Schema 继续递归，`enum`/`const`/`required` 等数据原样保留 | `test_business_field_named_title_keeps_its_constraint`、`test_business_field_named_description_keeps_its_constraint`：均为 `MODEL_OUTPUT_INVALID` 且 `calls=[]`；`test_frozen_structure_without_titles_is_accepted` 仍通过（普通文档注释差异照旧可接受） |
| `task_output_schema` 直接返回全局嵌套字典引用，`schema_matches_task` 又读同一对象：调用方改动自己拿到的 Schema 会同时改掉校验基准，副作用持续影响其他调用方 | getter 返回 `copy.deepcopy`，冻结基准 `TASK_OUTPUT_SCHEMAS` 不再对外暴露可变引用；`schema_matches_task` 的期望值仍取该冻结基准 | `test_task_output_schema_getter_does_not_expose_the_frozen_baseline`：改过的 Schema（加 `consumer_tag`）被拒且 `calls=[]`，随后另一调用方用原本正确的 `ProfileContent.model_json_schema()` 仍正常返回 `ok` |

上述 3 条用例在修改前逐条复现失败（旧实现放行/污染基准），修改后通过。本轮只动 `llm/schemas.py` 的比对与取用逻辑及其用例，未改网关端口、DTO、契约、依赖或真实适配器范围。
