# IN-03：PDF / DOCX 文件读取

关联 [Issue #17](https://github.com/Riverstar123/ResumeDoctor/issues/17)。
实现范围为 C 的 M3、对应测试、模块说明和后端依赖；本地任务分支为
`codex/17-document-extraction`。本变更提交 A/D 评审；合并和 Issue 关闭由后续验收决定。

## 能力与边界

真实读取 PDF 页文字、DOCX 正文及表格，并返回文本、来源片段及告警。
PDF 定位为 `page:1`；Word 定位为 `paragraph:1` 或
`table:1/row:1/cell:1/paragraph:1`，嵌套表格与内容控件带独立层级。
表格行/单元格可被内容控件或受支持的包装层包裹；按可读内容顺序编号，
在表格成员边界停止查找，嵌套表格由所属单元格单独处理，不展开成外层行。
所有片段按换行合并成 `ExtractedDocument.text`，引用校验针对这份实际提取原文。
PDF 的复杂多栏、图形和字体编码可能影响阅读顺序，草稿仍需用户确认。
DOCX 不读取页眉页脚及脚注尾注，存在时明确返回告警，不声称完整保留排版。

仅支持文字 PDF / DOCX，不做 OCR，不处理带密码 PDF、旧 DOC 或含宏 Word。
全部无文字时返回 `NO_TEXT_LAYER`；部分 PDF 页没有文字时，返回页码告警，
不把空页或扫描页补成经历。HTML/提示词文本只作为资料读取，不执行其中的命令。

## 限额与失败处理

| 限制 | 默认值 | 超出行为 |
|---|---|---|
| 输入文件 | 10 MiB | `FILE_TOO_LARGE`，不启动解析 |
| PDF 实际页数 | 20 页 | `DOCUMENT_PARSE_FAILED` |
| PDF 内容流 / DOCX 声明与实际展开总大小 | 10 MiB | `DOCUMENT_PARSE_FAILED` |
| DOCX 内部成员 | 1024 | `DOCUMENT_PARSE_FAILED` |
| 提取正文 | 30,000 字符 | `INPUT_TOO_LONG`，不静默截断 |
| 非空片段 | 5000 | `DOCUMENT_PARSE_FAILED` |
| 子进程解析等待 | 10 秒 | 结束并回收进程，返回 `DOCUMENT_PARSE_FAILED` |

Word 实际页数依赖排版引擎。本次用户明确接受轻量方案：检查记录的显式分页，
用大小、展开量、条目数、文字量和超时约束保护；每次返回
`DOCX_PAGINATION_UNVERIFIED`，不承诺实际排版不超过 20 页。
`docProps/app.xml` 中的页数不能用作合格证明。
**这与任务中未区分格式的“20 页”要求存在明确例外，需 A/D 在评审中确认；
不以本地用户同意替代团队验收。** 若要求严格 Word 排版页数，应另行评估受限的
排版服务，或引导用户转为 PDF；本轮没有安装额外排版软件。

ZIP 仅在内存中访问，不解压到路径；全部条目均有界读取并核对 CRC，避免忽略未提取的损坏图片。
拒绝重复成员、路径穿越、Windows 路径、
符号链接、加密条目及非标准压缩方式。XML 禁用 DTD、实体展开和外部实体。
PDF 解码器的展开上限仅在子进程内收紧，避免修改 API 进程的库全局配置。
解析异常、原文和文件路径不写到子进程 stderr 或公开错误中。
独立进程提供可终止性，不代表另建了操作系统安全沙箱或完整的内存资源隔离。

## M2 / M5 集成交接

现有 `IntakePort`、HTTP OpenAPI、共享 DTO 均未改变。
借用流不被关闭；对可定位流恢复原位置，对不可定位流从当前位置读取。
本模块不保存、删除原文件，也不把文件发送给供应商。

M2 可以按以下顺序消费具体实现：

```python
from app.contracts.ports import TaskContext
from app.intake import GatewayIntake

intake = GatewayIntake(gateway, source_id=reserved_document_id)
document = await intake.extract_document(borrowed_stream, media_type)
draft = await intake.build_document_profile(
    document, context=TaskContext(model_id=model_id)
)
```

便利方法内部调用原有 `build_profile`，再由原文确定定位。已有调用方也可以使用
`locate_document_evidence(draft, document, reserved_document_id)`，无需新增共享协议。
引用在合并全文中出现多次（含同一片段内重复、重叠命中）或跨片段时不猜位置，
定位保留为 null；只有全文唯一命中且完整落在同一片段内才填写定位。
调用方提供的全文与按换行连接的片段不一致时，不猜测片段偏移，定位保留为 null。
原始证据引用仍可核查。
原档案和其他来源的证据不被改写，不把模型给出的页码当作可信定位。

`reserved_document_id` 必须由 M2 为当前请求生成并持久化；不得把一个全局固定来源
编号用于所有用户或所有文件。M2 需决定如何保存/展示 `warnings`，尤其是 Word 页数
未核验、未读取页眉页脚和 PDF 空文字页的提示，不能静默当成完整提取。

已同步主分支 PR #47 的 P1 装配：`make dev` 使用 `SyntheticIntake` 合成提取，
真实文件解析尚未装配到该入口，且 `task_error` 不直接识别 `IntakeError`。
真实装配时 A 需将 M3 的错误映射到现有 HTTP/Task 安全错误；文件过大/不支持类型应在
入队前按已有 413/415 处理，解析阶段的异常按既有后台码安全映射。
本轮没有改动 M2 平台，也不声称浏览器上传已经接通真实解析。
M5 的固定 FakeModelGateway 只能处理合成样例；从任意文件生成档案的模型语义效果
和真实供应商隐私策略仍需后续任务验证。自动测试用受控 StubGateway 验证数据链路。

## 验证方法

使用项目锁定环境：

```powershell
uv sync --project backend --locked
uv run --project backend --frozen pytest -q backend/tests/intake/test_documents.py
uv run --project backend --frozen pytest -q backend/tests
uv run --project backend --frozen python -m app.tools.check_contracts
uv run --project backend --frozen ruff check backend
uv run --project backend --frozen ruff format --check backend
git diff --check
```

Windows 的受限沙箱可能阻塞 asyncio 的本地事件循环/子进程机制；本轮实际测试
在已授权的沙箱外运行，所有资料为运行时生成的合成内存字节，无真实供应商调用。
Windows 调用环境需支持 asyncio 子进程（默认 Proactor 事件循环）；不支持的事件循环
会安全失败，不能改用仅取消等待、实际仍在后台解析的线程作为兜底。
测试文件以合成内存字节为主；少数临时目录结束后清理，不提交二进制简历或测试输出。

- 最终完整后端测试：**379 passed**，其中本任务解析套件共 44 项；现有接口、评分、
