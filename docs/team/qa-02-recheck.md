## 发现与修正

### 1. 普通及调试日志中的隐私泄露可能漏检

原检查直接断言 `caplog.text` 不含原文，但 pytest 默认只捕获 WARNING 及以上。
如果应用用 INFO 或 DEBUG 打印简历/密钥，原断言可能仍然通过。

修改位置：[输入安全测试](../../backend/tests/intake/test_security_acceptance.py)、
[数据库安全测试](../../backend/tests/platform/test_security_acceptance.py)。
相关场景开始前将 `app` 日志捕获设为 DEBUG，覆盖当前应用的网关、Worker 和仓库等
`app.*` logger；pytest 在用例结束时恢复设置。没有人为启用外部库的 SQL 参数调试。

验证不是只看正常测试变绿：用只存在于独立测试进程内的插件，向应用 logger
分别注入 INFO、DEBUG 级别的合成原文标记，没有修改实际应用文件。

| 实验 | 原检查 | 补强后 |
|---|---|---|
| 注入 INFO 原文日志 | 错误地通过 | 原文断言失败，成功发现问题 |
| 注入 DEBUG 原文日志 | 错误地通过 | 原文断言失败，成功发现问题 |
| 移除注入，运行实际代码 | 首轮通过 | 输入与资源检查 19 passed；真实 PostgreSQL 安全检查 8 passed |

上表两个失败是故意注入问题后的预期结果，不能算成正常代码测试失败。
这验证的是当前应用日志检查能力，不代替真实供应商 SDK 的日志验收。

### 2. 外站相同 API 路径可能被测试误当本站接口

原模拟只按 `/api/v1/...` 路径匹配，不检查 URL 来源。
如果客户端误连外站的相同路径，模拟仍可能给出成功数据，漏掉发错站点的问题。

修改位置：[浏览器安全测试](../../frontend/tests/e2e/security.spec.ts)。
现在使用唯一的浏览器上下文级请求处理，先核对配置的本站来源，再处理模拟 API。
非本站 HTTP(S) 请求被记录并阻止；其他三个正常场景要求外发记录为空。
没有用优先级更高的页面 API 模拟绕过来源检查。

新增反例同时请求外站的相同 API 路径与另一个外站图片，检查：

- 请求确实被来源检查记录并阻止；没有进入本站 API 模拟。
- 低优先级网络陷阱没有被触发，防止只靠兜底阻止而假通过。
- 陷阱保留用于实验失效时阻止联网，不向外站发送请求。

只在隔离副本临时禁用来源判断时，新增反例如期失败：外站 API 被错误地返回成功。
恢复后核对源码与副本指纹一致，再运行全部四项页面检查，全部通过。
该反例验证的是测试拦截器及网页行为，不是服务端权限或真实模型验收。

### 3. 重试时可能用旧错误提示提前满足断言

原检查点击“重新读取”后立即查相同的错误文字，可能在第二次响应处理前，
就被仍然存在的旧提示满足。

现在每次模拟 404 使用新的请求编号；重试前挂好响应等待，收到并完成第二个响应后，
要求页面显示**该响应的新编号**，再检查错误码、旧报告、证据和导出按钮均无残留。
旧错误提示不能再满足这些断言。
